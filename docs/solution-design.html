Solution design

Agentic SDLC Platform

A governed pipeline for agent-run software delivery. Agents propose; deterministic code decides; humans approve what carries risk; and every decision keeps the evidence that produced it. This is the architecture and the principles it rests on. What has been built so far, and what that proves, is section 13.

13 lifecycle phases 10 ports · 16 adapters Control plane + execution plane Reference implementation: one cycle proven end to end

1 · Purpose

A delivery pipeline assumes four properties of the work passing through it. An agent violates all four. Everything in this design is a mitigation for one of these rows.

Pipeline assumesAn agent doesConsequence
Deterministic outputSame input, different outputCannot diff, replay, or regression-test the pipeline itself
Bounded blast radiusEdits whatever appears relevantNo containment; review burden scales with output
Explicit provenanceReasoning is not an artifactCannot answer "why did this ship"
Failure is loudProduces plausible wrong outputFailures stay invisible until they are expensive

The platform runs the lifecycle as a state machine, lets agents propose at every step, and puts a deterministic predicate between every proposal and its consequences.

The governing principle

No model is ever in a position to approve its own work. Every yes/no decision in the system is made by code you can read, or by a person whose identity is recorded.

Two constraints shape the rest. The platform must work inside a client's existing toolchain rather than replacing it, because the code, the credentials, the runners and the compliance sign-off already live there. And every integration must be swappable, because no two clients have the same stack — one is on Jira and Jenkins, the next on Azure DevOps, and neither is going to move for us.

2 · Architecture principles

Eight stances. Everything else in this document is a consequence of one of them, and where a later decision looks arbitrary it is usually because a principle here made it inevitable.

P1Agents propose, deterministic code decides

Every gate — testability, change review, pass/fail, release readiness — is plain code with no model in it. An agent that could approve its own output would make the whole audit trail decorative.

P2Own the decisions and the evidence; borrow the execution

The platform holds run state, gates and evidence. Real work runs in the client's existing CI, where the code, credentials and controls already are. Owning execution is how a platform like this dies in an enterprise.

P3The ontology is fixed; the integrations are pluggable

Node and edge types are part of the platform and clients cannot redefine them, or no phase logic would be portable. Which system a criterion lives in is an adapter's problem. Clients extend through namespaced types the platform stores but never reasons about.

P4Identity is derived, never allocated

A node's id is a function of what it is — type, source system, native identifier. Two components that never talk to each other arrive at the same id for the same thing, with no coordination and no round trip.

P5Evidence is a byproduct of gating, not a separate step

Each phase already knows the relationships it creates at the moment its gate decides, so it asserts them then, stamped with the run that made them. There is no crawler and no reconciliation job, and the record cannot describe something that did not happen.

P6Declare the contract; never let an agent infer it

What data may exist, which selectors are on which screen, what an endpoint returns — all declared alongside the requirements. Every one of these was once implicit, and every one produced a confident, wrong answer that cost a full test run to discover.

P7Fail closed, and say why

An unsatisfiable plan, an unparseable change, a job that never reports — each stops the run with a reason a human can act on. Proceeding on a guess is the failure mode that destroys trust in an automated pipeline, because it is invisible until it is expensive.

P8Architecture is asserted by tests, not documented in comments

Core purity, adapter isolation and import boundaries are subprocess assertions in the suite. Every one of these boundaries is one hurried afternoon away from being crossed, and a comment does not fail a build.

3 · The two planes

The system is two planes and a boundary. The control plane is long-lived and owns decisions, state and evidence. The execution plane is ephemeral, runs inside the client's CI, and is where agent-authored code actually executes. Nothing above the boundary runs untrusted code; nothing below it holds a credential that can change a decision.

Control plane owns
  • Run state, resumable across restarts and deploys
  • Every pause: for a person, or for a remote job
  • The audit trail and the context graph
  • Which adapter each integration resolves to
Execution plane owns
  • The real work: build, test, scan, migrate, deploy
  • Executing agent-authored code, under the client's controls
  • Producing a structured result and durable evidence
  • No credential that can alter a decision

The seam between them

A phase hands work to the execution plane and parks. Results are pulled, never pushed.

DirectionMechanismCarriesAuth
Control → executionworkflow_dispatch or provider equivalentrun id, phase, correlation nonce, commit range, changed pathsPlatform credential
Execution → controlPolled: run conclusion + state artifactVerdict, scenarios, evidence refs, graph assertionsPlatform credential — result is fetched, not received
Optional nudgeUnauthenticated POSTRun id only, no dataNone needed — it can only trigger an earlier poll

Consequences: no inbound network path is required, so the control plane can sit behind a firewall with no ingress; there is no shared secret to rotate and no callback signature to verify; and a lost callback is not a lost run, because the poller reconciles regardless.

Correlating an asynchronous result

workflow_dispatch returns no run identifier. The platform mints a nonce when it reserves the dispatch row, plants it in the job inputs, and resolves the run by matching it against recent runs of that workflow. The nonce is owned by the caller, not the adapter — an adapter that generated its own would tag the remote job with an identifier nothing on this side could match back.

4 · The delivery lifecycle

Thirteen phases from demand to production feedback, in five stages, with a loop back from what production tells you.

The verification phases are drawn stacked because they should run concurrently against one change. Fan-out and join is the one structural change the graph still needs; everything else in the lifecycle is a new node against machinery that already exists.

5 · Anatomy of a phase

Every phase has the same four parts. That uniformity is the reason the remaining phases are work rather than research — and the reason a client can add one of their own.

PartWhoWhat it produces
ProposeAn agent, constrained to a declared output shapeA plan, a design, a change, a verdict — never an action
DecideDeterministic code, no modelAccept, or reject with a reason the agent can revise against
RecordThe phase itself, as its gate decidesAudit entries, evidence, and typed edges in the context graph
ApproveA person, at a tier set by riskA decision attributable to a name

The predicates, as implemented

The containment term in change_review is the one only the graph makes possible. Without it, "the agent edited something nobody agreed to" is a code review opinion; with it, it is a build failure.

6 · Governance model

Three mechanisms carry the governance claim, deliberately different in kind.

A deterministic core that agents cannot reach

Gating, scoring and state transitions live in a core that never imports a model client, directly or transitively. A test asserts it in a clean subprocess for every core module, and exactly one file in the codebase may import the model SDK.

Exactly one place pauses the pipeline

All pause and resume logic lives in one controller, with two entry points: one waits for a person, one waits for a remote execution. Keeping both there makes "the pipeline stopped here, and this is why" a single readable code path rather than a property scattered across a dozen nodes.

Risk-tiered approval

Requiring a human at every boundary is right for a demonstration and wrong for a team merging daily — they will switch it off wholesale. The gate is always evaluated; policy decides whether a person waits.

TierTriggerBehaviour
AutoLow blast radius, high confidence, deterministic checks greenProceeds; recorded with the evidence that justified it
NotifyModerate risk, or a pattern seen for the first timeProceeds, posts to the owning team
ApproveRegulated surface, migration, public contractPauses for a named person
Two-personProduction deploy, data migration, security-relevant changeTwo approvers, neither the author
Dependency

Tiering is only as good as the confidence signal it routes on. A defensible score is composed of things you can point at — deterministic check outcomes, whether retrieval grounded the answer, agreement between independent samples, historical accuracy for this phase and repository. Never a model's self-report, and never presented to a person as measured when it is not.

7 · The context graph

Every phase needs to know what the system already contains and how it is connected. Without a shared layer each one re-derives that from a diff and a prompt, and nothing a phase learns survives into the next. That does not scale to thirteen phases.

The rule that makes it work with any client stack

The graph owns identity and relationships. It never owns content. Requirement text stays in the client's tracker, code stays in the repository — the graph holds a stable id, a typed external reference, and only the attributes the platform gates on.

A graph that stored requirement text would duplicate the system of record and drift from it within a week. One that stores a pointer and a thin projection cannot drift, because it asserts nothing the source also asserts.

Three layers, and only the middle one is pluggable

  • The ontology is fixed — fifteen node types and sixteen edge types, each with a signature enforced when an edge is written.
  • Resolution is pluggable — an adapter maps a native identifier to a graph identity: this Jira key is a requirement, this path is a component.
  • Extension is bounded — clients add namespaced types that are stored and displayed but never gated on.

15 node types, 16 edge types. Signatures are validated at write; an edge in the wrong direction is rejected, not stored. Every edge carries the run and phase that asserted it, and is superseded rather than rewritten.

Identity

NAMESPACE = UUID("6f2a1c7e-9b3d-4a52-8f61-0c4d7e5a2b19")

def node_id(node_type: str, system: str, external_id: str) -> str:
    return str(uuid5(NAMESPACE, f"{node_type}|{system}|{external_id}"))

Derived rather than allocated, so both planes name the same entity with no round trip and ingest is idempotent without a dedupe pass. The function is duplicated across two packages that cannot import each other; a test imports the other copy by path and asserts they agree, because silent divergence would leave every cross-plane edge pointing at a node that does not exist and nothing would error.

Three graphs, one identity layer

What it makes possible

  • Release readiness becomes a query. "Every criterion traced to a passing test" is the one gate a regulated client actually asks about, and it is not answerable from a run log.
  • Regression scope is derived, not guessed. Testing widens from what a diff touched to what depends on it.
  • Change is contained. An agent editing a component the design never named is caught before the change is proposed.
  • Incidents trace back through component to criterion to requirement, and re-enter the lifecycle as evidence.

    async def complete(self, system, user, *, max_tokens) -> LLMResponse
    async def complete_json(self, system, user, schema, *, max_tokens) -> BaseModel

SourceControl has no merge method by design. A change is proposed; what happens to it is the client's existing review process.

How the boundary survives contact with delivery

Pluggability always erodes under pressure — somebody needs a value quickly and imports the concrete thing where it is convenient. Three assertions make that a build failure rather than a code review conversation: no core module may import a model client; only an adapter may speak HTTP; and importing the core must not pull any concrete integration into memory. Adapter construction uses a lazy import inside each factory branch, which is what lets those assertions hold at all.

9 · Data model

Run state, the audit trail, the graph, and a checkpoint store. The split matters: the checkpoint is how a run resumes, the tables are how a run is queried and audited, and conflating them would make the audit trail depend on a serialization format.

10 · Trust & security

The threat is specific: untrusted input reaches a model, and the model's output is executed as code on a machine that holds credentials. Four controls, in decreasing order of how much weight they carry.

ControlStopsStrength
Privilege split across two jobsGenerated code reaching a token that can writeStructural — enforced by the platform, not by review
Results pulled, never pushedA forged result becoming run stateStructural — no signature to get wrong, no secret to rotate
Deterministic change reviewA change touching what nobody agreed toStrong — the design's named components are checkable
Static allowlist on generated testsObvious exfiltration and subprocess pathsDefence in depth — a text scan, and a determined author can phrase around it

Secrets stay in the environment. The console reports whether each is configured and never returns or accepts a value — writing credentials into an application database is not something to do before there is a secrets manager behind a port.

11 · Deployment

One codebase, two topologies. The difference is entirely which adapters are configured.

Laptop — demonstration and development
  • API and console as two local processes, file-backed storage
  • Mock model provider — runs with no key at all
  • Simulated execution, or the real pipeline against a local checkout
  • Fully offline, which is exactly when a demonstration must not depend on a tunnel
Client environment
  • Same processes; managed database via the audit port
  • Model through the client's own tenancy
  • Execution dispatched to the client's CI
  • No inbound path required, so it can sit behind a firewall

Operational characteristics

Inference is not the bottleneck and is unlikely to become one. The dominant costs are building the application under test and running a browser suite, both of which belong to the execution plane and scale with the client's CI rather than with us.

12 · Design decisions

The choices that would be expensive to revisit, and why they went the way they did.

D1A pause is a pause, whoever is answering

Waiting for a remote job reuses the same machinery as waiting for a person, through a second method on the same controller.

BecauseParking a thread until an external actor answers is not human-specific. Reusing it meant checkpointing, thread identity, the duplicate-launch guard and the event stream all kept working — and the rule that exactly one place pauses the pipeline survived.

D2Pull results, never accept pushed ones

The platform fetches outcomes with its own credential. Any callback carries a run id and no data.

BecauseNothing a stranger sends can become run state, a lost callback is not a lost run, and it works on a laptop where CI could never reach a local URL.

D3Auto-approval applies to people, never to machines

Headless mode skips the human gates. It does not skip waiting for a job.

BecauseThe flag exists so a run does not stop for a person. It cannot manufacture the result of a job that has not run, and a mode that fabricated one would make every headless result meaningless.

D4An agent returns whole files, not a diff

The implementation phase asks for complete file contents and reconstructs the change itself.

BecauseA patch that does not apply is a failure with no useful message. Whole files always apply, and the review that follows can check them properly.

D5A change is proposed, never merged

The platform opens a branch or a pull request and stops.

BecauseWhat happens to a change is the client's existing review process. A platform that merged its own work would be asking to be switched off.

D6Test the change, not the working copy

Verification runs against a checkout of the branch under test.

BecauseAnything else diffs the change and then exercises the code from before it — a pipeline that appears to work and proves nothing.

D7Gates and dispatches are never retried or fallen back

The reliability wrapper protects business nodes only.

BecauseA paused node is not a transient failure. Falling back would mean recording an approval nobody gave, or a verdict no test produced — precisely what this system exists to prevent.

13 · What is built, and what it proves

A reference implementation exists. Its purpose is not to be the product — it is to establish that the architecture above survives contact with a real model, a real browser and a real repository, and to find the places where it does not.

The claim

One full cycle runs end to end: a requirement becomes a reviewed code change, tests scoped to that change and its blast radius prove it, and a release is recorded against the criterion it satisfies. Everything below was observed, not designed.

The cycle, as it ran

Afterwards the graph answered the release-readiness question directly: no acceptance criterion left without a passing test. The change the model produced was four lines, idiomatic, and touched nothing else.

The QA phase in detail

The most complete phase, and the reference every other one should follow. Eight nodes, of which two are deterministic gates with no model involved.

Also built

  • The context graph, populated from real repositories. Point it at a GitHub repository and it derives components and dependencies from source — 25 components and 41 dependencies from one production codebase, with its layering visible in the output.
  • A console with a dashboard, a runs view, the graph, and configuration that applies without a restart.
  • Ten ports and sixteen adapters, with an offline default for every one, so the whole system demonstrates with no keys and no network.

What the reference implementation proved by failing

Four findings only a real run produces, each now fixed and covered by a test:

  • Implicit contracts produce confident, wrong answers. An agent told a selector exists, but not which screen it is on or what values it accepts, guesses — and a wrong guess costs a full test run to discover. Everything an agent needs is now declared beside the requirements.
  • A pipeline that diffs a branch and tests the working copy proves nothing. Verification now runs against a checkout of the change.
  • Deterministic seeding and a live planner disagree about what data can exist. Plans now declare the data they need; the seeder guarantees it, or says it cannot.
  • Shared fixture data breaks once scenarios have conflicting needs. Cases needing absence intercept the response instead of reshaping the store.

Not built, and known

No authentication, so approvals are not yet attributable to a named person. No evidence store, so artifacts expire with the CI run that produced them. Confidence is a placeholder, so risk tiering cannot be switched on. Verification runs in sequence rather than in parallel. Each is on the roadmap in dependency order, and none of them is a surprise.

14 · Roadmap

Ordered by dependency, not by appetite.

1

Identity, and the audit schema that depends on it

Approvals attributable to a named person. First, because it rewrites the audit tables, and doing that once there are runs worth keeping is far more expensive. Nothing ships to a regulated client without it.

2

Evidence store, and the edges that point at it

Durable artifacts with a retention policy the client sets. An edge pointing at an expired CI artifact is not traceability, so these are one piece of work.

3

One live run against a client's own CI

The seam is proven against a local pipeline. Driving a real workflow in a real repository is the outstanding acceptance criterion — and the platform can already do it without that repository changing.

4

Parallel verification, starting with security scanning

Fan-out and join in the graph, then security as the second verification phase. The structural change first, because adding three more phases to a sequential chain makes each wait for the last for no reason.

5

Real confidence, then risk-tiered gating

In that order. Policy routing on a fabricated score is worse than no policy, because it looks defensible in a demonstration and fails in an audit.

6

Code review, release readiness, post-deploy verification

The remaining phases, each a new node against machinery that already exists. Release readiness is where the graph becomes a gate rather than a report.

7

Eval harness, code intelligence, the feedback loop

The harness first, so a model or prompt change can be told apart from a regression. Then blast-radius selection at scale, and runs triggered by production signal — which closes the lifecycle and is the point where this stops being a pipeline and becomes a system.

Sections 1 to 12 describe the architecture and the principles behind it, independent of how much of it exists. Section 13 is the reference implementation, written from observed runs: where it says something is real there is a test that fails if it stops being real, and where it says something is absent, no amount of reading the code will find it.
