Solution design

Agentic SDLC Platform

A governed pipeline for agent-run software delivery. Agents propose; deterministic code decides; humans approve what carries risk; and every decision keeps the evidence that produced it. This is the architecture and the principles it rests on. What has been built, what it measures, and what it does not yet do is section 15.

  • 13 lifecycle phases
  • 11 ports · 18 adapters
  • Control plane + execution plane
  • 583 tests · impact accuracy measured against a corpus

1 · Purpose

A delivery pipeline assumes four properties of the work passing through it. An agent violates all four. Everything in this design is a mitigation for one of these rows.

Pipeline assumesAn agent doesConsequence
Deterministic outputSame input, different outputCannot diff, replay, or regression-test the pipeline itself
Bounded blast radiusEdits whatever appears relevantNo containment; review burden scales with output
Explicit provenanceReasoning is not an artifactCannot answer “why did this ship”
Failure is loudProduces plausible wrong outputFailures stay invisible until they are expensive

The platform runs the lifecycle as a state machine, lets agents propose at every step, and puts a deterministic predicate between every proposal and its consequences.

The governing principle

No model is ever in a position to approve its own work. Every yes/no decision in the system is made by code you can read, or by a person whose identity is recorded.

Two constraints shape the rest. The platform must work inside a client’s existing toolchain rather than replacing it, because the code, the credentials, the runners and the compliance sign-off already live there. And every integration must be swappable — including the agents themselves, since a client with their own coding agent will want it doing the work and this platform deciding whether the work is admissible.

2 · Architecture principles

Nine stances. Everything else in this document is a consequence of one of them, and where a later decision looks arbitrary it is usually because a principle here made it inevitable.

P1Agents propose, deterministic code decides

Every gate — testability, change review, pass/fail, release readiness — is plain code with no model in it. An agent that could approve its own output would make the whole audit trail decorative. This holds whoever supplied the agent, and holds a client’s agent slightly more strictly: it is the only one that can change without anyone here knowing.

P2Own the decisions and the evidence; borrow the execution

The platform holds run state, gates and evidence. Real work runs in the client’s existing CI, where the code, credentials and controls already are. Owning execution is how a platform like this dies in an enterprise.

P3The ontology is fixed; the integrations are pluggable

Node and edge types are part of the platform and clients cannot redefine them, or no phase logic would be portable. Which system a criterion lives in is an adapter’s problem. Clients extend through namespaced types the platform stores but never reasons about.

P4Identity is derived, never allocated

A node’s id is a function of what it is — project, type, source system, native identifier. Two components that never talk to each other arrive at the same id for the same thing, with no coordination and no round trip.

P5Evidence is a byproduct of gating, not a separate step

Each phase already knows the relationships it creates at the moment its gate decides, so it asserts them then, stamped with the run that made them. There is no crawler and no reconciliation job, and the record cannot describe something that did not happen.

P6Declare the contract; never let an agent infer it

What data may exist, which selectors are on which screen, what an endpoint returns — all declared alongside the requirements. Every one of these was once implicit, and every one produced a failure that looked like a defect and was not.

P7Fail closed, and say what is missing

A gate that cannot check something refuses. An empty graph does not mean “nothing to object to”; an unmapped file path does not mean “nothing to contain”; an index that resolved four fifths of a codebase cannot produce an impact set worth approving. Each of these was once a silent pass.

P8Derived data is rebuilt, not migrated

The code-intelligence graph is a function of a commit. Re-deriving it is cheaper and safer than migrating it, which is why it is kept apart from the traceability graph — that one is an audit record and is only ever appended to.

P9A control that has not been measured is a claim

Blast radius, coverage and capture rate are all numbers this platform asserts about itself. Each is now produced by a harness with a corpus and a baseline, and each is reported with what it cannot see. A control whose accuracy is unknown cannot carry the weight the rest of the design puts on it.

3 · The two planes

One boundary decides most of the rest. The control plane is long-lived and holds every decision. The execution plane is ephemeral, runs in the client’s CI, and executes agent-authored code. They exchange work through one seam.

Control plane owns
  • Run state, resumable across restarts and deploys
  • Every pause: for a person, or for a remote job
  • The audit trail and the context graph
  • Every deterministic gate
  • Configuration, projects, and which agent does what
Execution plane owns
  • Running agent-authored tests against a real application
  • Producing evidence: traces, screenshots, results
  • Nothing that survives the job
  • No write token, by construction

The seam is deliberately narrow and deliberately one-directional: the control plane pulls results rather than accepting pushed ones. There is no callback to authenticate and no shared secret to rotate, and a forged result cannot become run state because nothing outside the reconciler can write to it.

The same seam now carries three different kinds of remote work — a CI job, a client’s coding agent, and a client’s test-authoring agent — because they are the same problem: start work somewhere else and find out later how it went. One row per run and phase serves as the idempotency guard, the result queue and the timeout ledger at once.

The control plane holds decisions and evidence; adapters are the only code that speaks to anything outside it.

4 · The delivery lifecycle

Thirteen phases in five stages. Three pauses are for a person; one is for a machine. The machine pause is not optional and cannot be auto-approved — a job that has not run has no result to approve.

Five stages, three human gates, one machine pause. Approval of a gate is recorded against a person; the machine pause is resolved only by a result that was pulled.

5 · Anatomy of a phase

Every phase has the same shape, and it is the shape that carries the guarantee rather than any individual phase’s cleverness.

1

Assemble the request

The phase gathers what the agent may see — the module catalogue from the graph, the acceptance criteria, retrieved code, the blast radius. Assembled by the phase, never fetched by the agent, so a client’s agent cannot quietly widen what it looks at.

2

Ask an agent

Through a port. The default is this platform’s own agent, answering in-process. A client’s agent may answer an hour later into a pull request; the phase parks on the dispatch seam and is resumed by the reconciler. The phase branches on the outcome, not on which adapter is configured.

3

Decide, in code

A deterministic predicate. Does every module named exist in the graph? Does every file belong to a module the design claimed? Does every scenario have an outcome a test can observe? Does this spec import anything outside the allowlist? No model participates.

4

Revise, or refuse

Rejection reasons go back to the agent for a bounded number of attempts, because halting a run over one vague sentence is not a useful pipeline. A dispatched agent gets one attempt: a retry means another agent run, and the reasons a human needs are better read on the rejected proposal.

5

Assert what happened

The edges the phase created, stamped with the run and phase that asserted them. This is the whole of evidence collection — there is no separate step that could disagree.

6 · Governance model

Four gates, each a different kind of check, each failing closed.

GateDecided byRefuses when
1 · Requirements readyPersonThe demand is not yet clear enough to design against
2 · Design approvedCode, then a personA named module or file does not exist; a file is outside the modules claimed; a criterion is neither addressed nor excused; the graph is empty; the index resolved less than 80% of internal imports
Change reviewCode onlyAn edit lands outside the approved modules — or in a path the graph cannot attribute to any module at all
Test planCode onlyA scenario has no observable outcome, references an acceptance criterion that does not resolve, or needs data the store cannot provide
3 · Release readinessCode, then a personA required regression did not run or did not pass; a coverage claim the run disproves; a spec refused by the sandbox; the shared data store changed during a parallel run
Why fail-closed is a principle and not a preference

Three of these checks once passed silently in exactly the situation they existed for. An empty context graph approved every design, because there was nothing to object with. A file path the graph could not place was dropped from the set being checked, so a change made entirely of unplaceable paths skipped containment. And a coverage claim that a script covered a module was never compared against what the run actually exercised. A gate that cannot check something has to refuse, or it is decoration in precisely the case that matters.

7 · The context graph

One identity layer, three graphs with opposite durability requirements. Conflating them is the mistake that makes a traceability record depend on a nightly re-index.

Traceability is accumulated and audited. Code intelligence is derived and rebuilt. Retrieval is derived, rebuilt and disposable — nothing is gated on a retrieval score.

The ontology is 15 node types and 18 edge types, each edge legal only between a declared pair. An edge that does not typecheck is refused at ingestion rather than stored and reasoned about later.

What a node carries

Identity plus a thin projection — never content, because the client’s system stays the record. For source files that projection is enough to answer questions without re-reading the repository:

{"module": "demo-app/app/claims", "language": "typescript",
 "sha256": "6b67368…", "loc": 121, "exports": ["ClaimsPage"]}

Module nodes additionally carry the provenance of the index that produced them — the commit, the indexer version, when it ran, and how much of the codebase it managed to resolve. Every answer derived from the graph is only as good as that snapshot, so the snapshot has to be able to say what it was.

Edges are typed, not just present

An import edge is not one thing. Three distinctions turned out to matter, and each was found by measuring rather than by reasoning:

DistinctionWhy it changes an answer
kind: runtime | type-onlyA TypeScript import type is erased at compile time. Real coupling for a type checker, none at runtime — counting it overstates what a change can break.
from_test: true | falseRoughly a third of this repository’s import edges originate in test files. Ranking modules by raw fan-in ranks them by how well tested they are. Regression scoping wants exactly these edges; hub ranking must not.
provenanceStatically extracted, rolled up, or observed at runtime. A hand-written coverage claim and a recorded one must not look alike to whatever reads the graph later.

They are classified rather than filtered, because the right answer differs per consumer. Impact and hub ranking ask for runtime product coupling; regression scoping asks for the test edges specifically.

HTTP coupling, which no import edge expresses

The structural blind spot in a dependency graph built from imports: a frontend and the API it calls import nothing from one another. Measured on a sibling repository, there were zero edges between the web and api packages while five web files called the API — so a change to a route handler reported an impact set containing none of its callers.

Both halves are statically visible. A server declares a route — a Next.js file path, a FastAPI decorator plus its router prefix plus its mount prefix — and a client names it in a literal. Matching the two recovers the edge.

A change to a route handler reaches its callers only through the contract edge. On imports alone every route handler in this repository had zero dependents.

A URL assembled at runtime from configuration cannot be matched this way. Those are counted as unmatched calls rather than guessed at, so the amount of coupling still invisible is a number rather than an assumption.

Honest completeness

The index reports where every import statement ended up, in four buckets that sum to the total. This replaced a single counter that incremented only for unresolved relative imports — under which this repository reported “3 unresolved” while silently dropping 19 internal edges, because an aliased import that failed to resolve was indistinguishable from an npm package.

BucketCurrentMeaning
resolved433An edge exists
external package517Genuinely leaves the repository
unresolved, internal0An edge was dropped — the number that used to hide

8 · Impact analysis

The blast radius is the core claim of this architecture, so it is the thing most worth measuring rather than asserting. It is computed at file level and rolled up to modules for display — rolling up first and traversing after gives every file in a directory the same radius, which cannot distinguish a leaf from a hub, and that distinction is what impact analysis exists to make.

How good is it, actually

A harness holds out one file per commit and asks the graph which of its co-changed siblings it reaches. Ground truth is co-change, which is a proxy and is named as one: files change together for reasons no dependency graph models, and coupling the graph gets right may not appear in history yet. Two baselines make the number readable — “the whole repository” is the recall ceiling, and “files in the same directory” is the answer with no dependency analysis at all.

PredictorRecallPrecisionMean radius
graph, imports + contracts · depth 110.7%29.1%3.5
graph, imports + contracts · depth 214.4%21.1%6.7
graph, imports + contracts · depth 315.8%19.1%8.9
baseline: same directory14.6%15.3%15.0
baseline: whole repository100%5.4%211

Two things came out of this that argument had not. Traversal depth was one hop, and one hop sat below the directory baseline on recall — the earlier justification for it was noise control measured at module level, and at file level the trade is different. Two hops matches the baseline’s recall at 1.4× its precision and 45% of its radius, so the default moved to two, with the table above beside it in the code. And contract edges add recall at every depth, by a margin that widens as traversal deepens, which is what you would expect from an edge type that crosses a service boundary.

What this number is and is not

Absolute recall is low, and the corpus is small — 240 held-out cases from a handful of large feature commits, which is the shape where co-change carries the least coupling signal. This is a floor and a regression detector, not a claim to accuracy. Until it has run over a real client history, the defensible framing is derived first-order impact, measured against co-change. The dependency edges can be incomplete, falsely resolved, and blind to anything that is not an import or a matched route.

9 · Test selection & coverage

The blast radius is only a control if something acts on it. For a long time it was not: the impacted modules and the scripts covering them were interpolated into a planning prompt as “worth reusing as regression”, and nothing verified the result. An agent could omit every one and the run still passed.

Required, not suggested

Scripts covering an impacted module are installed into the run by code. The agent is told to skip them and spend its scenarios on the modules nothing covers. The gate then enforces three things, and any of them failing fails the run:

required ⊆ ran     ∧     every required script passed
coverage a script claims  ⊆  what the run was observed to exercise

The second line is the one that catches drift. A script that passed while never requesting the module it is credited with is a coverage record a gate will trust and that is not true.

Coverage is observed, not declared

Playwright already records a trace per test, and that trace contains every request the test made. Reading them afterwards gives measured coverage with no changes to the specs — which matters, because a spec may only import the test framework and hanging a fixture off it would weaken the sandbox that keeps generated code contained.

Coverage is attributed from what the run requested, through the route map the graph carries, to source files. An intercepted request earns nothing.

The measurement immediately contradicted the hand-written manifest it replaced: every script under-declared, because they exercise the API and the layout as well as the page they claim. And one distinction is load-bearing — a test that answers a request itself with interception never reaches the handler, so crediting it would write a false claim that reconciliation could never catch, because the interception happens on every run.

Coverage is reported at file level

Module granularity hides the answer. A module holding both a layout and a home page reads as covered the moment any page test runs the layout, while the home page has never been visited. Both are reported; the file list is the honest one.

The suite accumulates

Generated specs used to be written, run once and deleted, so the library never grew and the pipeline spent a model call per scenario per run re-deriving tests it had thrown away. A passing generated spec is now a promotion candidate carrying its own source, a checksum and its provenance — because the job that produced it is a CI runner that disappears, and a path into its filesystem is dead by the time anyone reads the candidate. Promotion re-verifies the checksum and re-runs the sandbox validator before writing anything into the library.

What isolation this does and does not give

Scenarios share one mutable data store and the runner is parallel by default. Restoring the store after a run protects the checkout; it is not test isolation. Nothing here can give scenarios a private store without changing the application under test, so instead: mutating calls are detected in the spec source and a run containing any of them gives up parallelism, and the store is compared before and after so a mutation the analysis did not recognise still fails the gate. Prevention by analysis, detection by measurement — and stated as a limit rather than presented as isolation.

Substituting an agent, not just an integration

The interesting case is a client who has their own coding agent and wants it doing the work while this platform decides whether the work is admissible. That is a port like any other, with one wrinkle: an in-process agent answers in seconds and a cloud agent answers in hours, and both have to fit one contract.

One contract, two latencies. The default is the platform’s own agent; a client’s is a configuration change, and the review afterwards is identical.

Containment becomes detection, and the difference is stated

An in-process agent returns edits and can be refused before they reach a branch. A cloud agent works in its own environment and opens its own pull request, so nothing here can stop it writing. The branch exists whatever the verdict, and a refusal fails the run with it left for a human. Implying a control that is not there would be worse than not having it.

Which is why the design phase matters more, not less, when a client’s agent implements: a human approves a bounded scope before work starts, and the work is checked against it afterwards. If the design becomes something the agent writes and immediately acts on, containment stops being a control and becomes a promise.

How the boundary survives contact with delivery

Pluggability erodes under pressure — somebody needs a value quickly and imports the concrete thing where it is convenient. Three assertions make that a build failure rather than a code review conversation: no core module may import a model client; only an adapter may speak HTTP; and importing the core must not pull any concrete integration into memory. That third one is what forces adapter construction into a lazy import inside each factory branch.

The HTTP assertion earned its keep during this work: a router acquired an httpx import to catch a transport error, and the test failed it. Transport belongs to the adapter that speaks it — the GitHub adapter now wraps its own.

Selecting an adapter cannot break the platform

A configuration change once did. The value was persisted before anything checked it could be built, so an unbuildable choice was written to the database and then failed — a stack trace to the admin, and a process that would not start. The only way back was editing the database by hand, which is not a recovery path for a console whose API has to be up to offer one.

ControlGuarantees
Changes built in full before they are storedAn unbuildable configuration is refused with the reason, and nothing is written
A preflight endpointThe console can say what a choice needs while someone is choosing, not after they save
Three startup fallbacksWhat was asked for; the environment alone; every integration disabled. The platform always comes up, carrying what is running and why
A read-only reachability checkWhether the configured agent can actually be reached, without starting work that costs an agent run and opens a pull request

The property is enforced exhaustively rather than per adapter: every option of every selector is checked twice — refused without its credentials, building with them — and all 48 combinations together, because a combination is what an admin actually saves.

11 · Projects & data model

One deployment serves several engagements. That is a data-boundary problem before it is a feature: the graph was single-project by construction and silently so — indexing a second repository deleted the first, with no error, and the first team’s next design phase simply refused against an empty graph.

Scoping is carried in the node’s system field rather than a column, because identity is already derived from type, system and native id: qualifying the system makes two projects’ identical file paths distinct identities for free. Without it they collide and each index overwrites the other’s projections. The default project is deliberately unqualified, so a single-project deployment needs no re-index.

Every reader is scoped, not only the destructive paths. An unscoped module list would aggregate every client’s code into one answer, and unscoped impact would tell a design in one project that it reaches files in another’s codebase.

StoreHoldsNotes
projectsAn engagement: name, start date, and the settings that differ between clientsRepositories, branches, environments. Global settings could not hold two answers at once
runsStatus, the original demand, timestamps, the projectStamped at creation, not read back later — a run is a decision about one codebase
audit_logBefore/after per node, confidence, human decisionExactly one pair per logical node call, however many retries happened underneath
dispatchesRemote work: correlation, state, result, deadlineUnique per run and phase — idempotency guard, result queue and timeout ledger in one row
graph_nodesIdentity and a thin projectionNo content; the client’s system stays the record
graph_edgesTyped relationships with the run and phase that asserted themAppend-only; superseded, never rewritten
setting_overridesPlatform configuration set through the consoleWith a change history recording what each value was before
checkpointsSerialized graph state per threadSeparate store; a paused run survives a restart or a config change

Deliberately absent: authentication, membership, per-project secrets. Projects give containment; who may see or approve what needs an identity provider, and a half-built one is worse than none.

12 · Trust & security

The threat is specific: untrusted input reaches a model, and the model’s output is executed as code on a machine that holds credentials.

ControlStopsStrength
Privilege split across two jobsGenerated code reaching a token that can writeStructural — enforced by the platform, not by review
Results pulled, never pushedA forged result becoming run stateStructural — no signature to get wrong, no secret to rotate
Spec sandbox validationGenerated code importing a Node builtin, spawning a process, or reading the environmentStructural — refused before it can execute, whoever wrote it
Deterministic change reviewA change touching what nobody agreed toStrong in-process; detective for an agent that runs elsewhere
Secrets never round-tripA credential in a database or an audit trailStructural — the config surface reports presence only

The fourth row is the one to read carefully. Containment prevents an out-of-scope edit when the platform writes the branch, and detects one when a client’s agent does. Both fail the run; only one stops the code existing.

13 · Deployment

A FastAPI control plane, a Next.js console, and a checkpoint store. Postgres in anything real; SQLite is what makes the reference implementation start with no infrastructure. The execution plane is whatever the client already runs.

Configuration is applied by rebuilding adapters rather than restarting — the registry is a pure function of settings, so applying a change is rebuilding it, and paused runs survive because their state lives in the checkpoint store rather than in the compiled graph.

14 · Design decisions

D1Traverse impact at file level, roll up for display

Module-level traversal gives every file in a directory the same radius. Measured on one repository that was 13% of the codebase per change against under 1% at file level.

D2Two hops, chosen by measurement

One hop sat below the “same directory” baseline on recall. Two matches it at 1.4× the precision and 45% of the radius. The table is in the code beside the constant, and the harness is expected to be re-run before it changes.

D3Classify edges rather than filter them

Impact wants runtime product coupling; regression scoping wants the test edges specifically. Filtering at index time would force one consumer’s answer on the other.

D4The execution plane reads a generated export, not a database

It runs in client CI with no route to the control plane. The handover is a file carrying the commit it describes, so a stale copy is visible rather than silent. Hand-maintaining that file is what let every coverage claim in it name a script that did not exist.

D5Coverage mappings live with the scripts, and are observed

Which modules a script exercises is a property of the script. Asserting it in the graph is how modules came to claim coverage from scripts nobody had written; asserting it by hand at all is how a claim survives the code drifting away from it.

D6A dispatched agent is asked once

The revision loop is worth three attempts when each is a model call and not when each is an agent run. The reasons a human needs are better read on the rejected proposal.

D7Project scope lives in identity, not in a column

Identity is already derived from type, system and native id. Qualifying the system makes two projects’ identical paths distinct for free, needs no migration, and leaves a pre-existing graph readable as the default project.

D8The platform starts even when its configuration will not build

Three fallbacks, ending in one with no external dependency. A control plane that will not start cannot be used to fix the setting that stopped it.

15 · What is built, and what it proves

A reference implementation on a small application under test. The architecture above is what it is for; this section is what actually exists, and where the honest description differs from the ambitious one.

The full cycle, end to end

Requirement → design proposed and validated against the graph → human approval → implementation committed to a branch → QA scoped to the change and its blast radius → release recorded with the files it contained and the environment it reached. Run with a live model, against a real application, producing real Playwright evidence.

The mutation worth quoting

Making the claims API’s status filter case-sensitive left every page-level test passing — the page sends the exact string, so nothing it does is affected. Only the API contract test caught it. Without that script the run is green and a breaking change ships for every other caller. That is the failure mode the whole blast-radius argument is about, reproduced deliberately.

16 · Roadmap

Ordered by what most changes whether the architecture’s claims hold, rather than by what is most visible.

1

Run the accuracy harness against a client history

Every impact number here comes from one repository of large feature commits — the shape where co-change carries the least signal. A real history is what turns a regression detector into a figure worth quoting, and it is cheap: the harness needs a repository and a graph.

2

Symbol-level indexing

A language server behind the existing CodeIntelligence port. It is the change that would separate “a file changed” from “an exported signature changed”, and the harness is what should decide whether it earns its cost.

3

Identity, and the audit schema that depends on it

Approvals attributable to a named person, and projects that control access rather than only containing data. First among the enterprise items, because it rewrites the audit tables.

4

Requirements and test management through their ports

Criteria and contracts from the client’s system rather than a file in this repository — the last place the pipeline reads something it should have been given.

5

Per-scenario data isolation

Fixtures created and destroyed per test through the application’s own API, or a per-worker store. The current answer detects the hazard and gives up parallelism; it does not remove it.

Every figure in this document is produced by code in the repository — the capture rate by the indexer, the accuracy table by scripts/measure_impact.py, the coverage numbers by the evidence phase. Where a claim could not be measured, it is described as one.
